# Jeffrey Toolkit — Development Roadmap

This roadmap describes the intended evolution of Jeffrey without tying the project to one server, network, model, operating system or organisation.

The repository contains a **reference deployment**. Paths, ports, authentication, model files and hardware values shown elsewhere in the repository are examples from that deployment and must be adapted to the target environment.

## Design principles

1. Keep the model server local to the host where possible.
2. Keep client access behind a reverse proxy and an authentication layer.
3. Treat the browser/frontend as untrusted input.
4. Prefer deterministic validation for security artifacts generated by the model.
5. Keep the project usable without internet access at runtime.
6. Make every infrastructure change reversible.
7. Keep deployment-specific secrets, addresses, usernames, subnets and credentials out of the public repository.
8. Do not couple the toolkit to a single model or hardware profile.
9. Benchmark model/runtime changes on the target hardware before production use.
10. Preserve a known-good configuration while introducing major changes.

---

## Phase 1 — Production hardening and reproducible deployment

### Goals

- Run the model server with a dedicated non-root account.
- Apply appropriate systemd sandboxing.
- Make model files read-only to the service.
- Ensure the web content is not writable by the web server.
- Restrict exposed network services to the required source networks.
- Keep the model API bound to localhost unless there is a documented reason not to.
- Document egress expectations.
- Establish tested backup and rollback procedures.
- Make the reference deployment reproducible without embedding environment-specific values.

### Acceptance criteria

- Model server is not running as root.
- Direct access to the model API from client networks is blocked.
- Web content cannot be modified by the web-server account.
- SSH/management access remains available only from approved management paths.
- Reverse proxy configuration validates cleanly.
- Health checks work.
- Rollback has been tested.
- No model change is required to complete this phase.

## Phase 2 — Gateway / middleware

Introduce a small local middleware layer between the reverse proxy and llama.cpp:

```
Client
  ↓
Reverse proxy / authentication
  ↓
Jeffrey gateway
  ↓
llama.cpp
```

The gateway should initially remain deliberately small:

- request validation
- size limits
- model/runtime parameter policy
- request IDs
- structured logging
- timeout handling
- health checks
- streaming passthrough
- consistent error responses

Do not turn the gateway into a large application framework without a demonstrated need.

### Suggested future request flow

```
HTTP request
   ↓
authentication at edge
   ↓
input validation
   ↓
request ID
   ↓
policy/context handling
   ↓
llama.cpp
   ↓
stream validation/error handling
   ↓
client
```

## Phase 3 — Structured output and deterministic validation

LLMs should not be the final authority for machine-readable security artifacts.

Start with one artifact type, for example Sigma:

```
User request
   ↓
LLM
   ↓
structured JSON
   ↓
schema validation
   ↓
Sigma parser/linter
   ↓
result
```

Extend later to other formats such as YARA, Suricata or Zeek where appropriate.

The principle is:

> The model proposes; deterministic tooling validates.

---

## Phase 4 — Local knowledge / RAG

Add local retrieval only after the gateway is stable.

Potential sources:

- MITRE ATT&CK
- Sigma
- LOLBAS
- local SOC procedures
- approved internal documentation
- CVE/KEV data imported through an approved offline process
- framework documentation

A simple local retrieval implementation can be sufficient initially. Avoid introducing a large vector database unless scale or retrieval quality actually requires it.

A useful first architecture is:

```
Question
   ↓
query normalization
   ↓
local retrieval
   ↓
top relevant documents/chunks
   ↓
LLM
   ↓
answer + source references
```

## Phase 5 — Deterministic security tooling

Where a task can be performed more reliably by a parser, compiler, linter or dedicated security tool, prefer that tool over free-form model output.

Examples:

- Sigma validation/conversion
- YARA syntax validation
- Suricata rule validation
- Zeek script checks
- JSON/schema validation
- IOC normalization
- hash/encoding/format validation

Tool execution should be explicitly allow-listed and sandboxed. Do not expose arbitrary shell execution to the model.

---

## Phase 6 — Offline knowledge and update pipeline

The target environment may be isolated from the internet.

Build a controlled update workflow:

```
Internet-connected staging system
        ↓
download
        ↓
verify checksum/signature
        ↓
package
        ↓
transfer through approved process
        ↓
offline validation
        ↓
test
        ↓
production
```

Keep runtime operation independent from internet connectivity.

The same principle applies to:

- models
- llama.cpp releases
- frontend libraries
- LOLBAS snapshots
- ATT&CK data
- CVE/KEV data
- other knowledge sources

---

## Phase 7 — Model benchmarking and routing

Model selection should be based on measurements on the actual target hardware.

Benchmark at least:

- time to first token
- prompt processing speed
- generation speed
- memory usage
- context length
- vision processing
- structured-output reliability
- long-document behaviour
- SOC-specific prompts
- Dutch-language performance if relevant

Only then consider:

- a newer model
- another quantization
- a smaller fast model
- a larger quality-focused model
- model routing
- speculative decoding / MTP where supported

Do not assume a newer or larger model is automatically better for a CPU-only or constrained deployment.

---

## Phase 8 — Operational maturity

Potential later additions:

- Prometheus-compatible metrics
- dashboards
- alerting
- configuration validation in CI
- automated regression tests
- release tags
- documented upgrade/rollback procedures
- change log
- security review checklist

The project should remain understandable and maintainable by someone who did not build the original system.
